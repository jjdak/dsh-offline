# 环境二：支持 x86-64-v2 的 CentOS 7 服务器调研

最新交付：[0.1.7-alpha.2 图片增强无语音版](https://github.com/jjdak/dsh-offline/releases/tag/dsh-v0.1.7-alpha.2-image-wasm.1)，源码 `00102833dfaee1da9f48a3a8eae9d34005a75218`。复用 alpha.1 的全部适配脚本与固定运行时输入，重新完成完整容器构建、归档审计、安装与 Web 验证，并通过最终归档的断网 CentOS 7 检查。alpha.1 仍保留；以下包含原始调研与首次适配记录。

升级提醒：有自定义 `spill-policy.maxInlineBytes` 配置时，需要改为 `maxInlineTokens` 并按 token 重设预算。本仓库安装模板未设置此项；共享数据路径不变，升级前仍应停止旧实例并备份数据。

本文说明另一台低版本内网服务器的适配调研。它不是现有 `text-only` 包原先面向的、不支持 x86-64-v2 的环境；本调研不修改现有包的兼容性承诺。

资料来源为用户保存的《调研 CentOS 7 兼容性》HTML 对话，整理日期为 2026-09-22。原始分享链接：<https://chatgpt.com/s/cx_6ab1f7ddd5888191ac0a192559df0956>。以下实测结果均为该对话记录中的报告，尚未在本仓库独立复现；HTML 没有包含其另附可行性报告的完整补丁和测试日志。

## 目标机已知条件

| 项目 | 调研中确认的信息 |
| --- | --- |
| 系统 | CentOS 7，glibc 2.17 |
| CPU | Intel Xeon Gold 6354 |
| 指令集 | 用户检查确认 `cx16`、`lahf_lm`、`popcnt`、`pni`、`ssse3`、`sse4_1`、`sse4_2` 均存在，按支持 x86-64-v2 评估 |
| 内核 | `3.10.0-1160.el7.x86_64` |
| Docker | 目标机不允许运行；外部构建、测试环境可使用 |
| 模型 | 用户提供的信息为内网 DeepSeek V4 Flash API，仅支持文本 |

CPU 支持 v2 消除了这台机器的一个限制，但没有消除 glibc 2.17、旧 C++ 运行库和 3.10 内核的兼容性问题。也不能据此认定环境一支持 v2。

## 调研已经报告的测试结果

测试基线为 dsh `0.1.5-rc.2`，用户态环境为 `centos:7.8.2003` 容器，容器共享宿主机的 6.12 内核。运行测试禁用了外部网络，模型调用使用本地模拟 API。

| 测试 | 调研记录的结果 |
| --- | --- |
| Web 服务及认证后页面访问 | HTTP 200 |
| 文本会话 → 模拟 API → 返回答案 | 通过 |
| 模拟模型调用 Bash → 临时文件读写 → 工具结果回传 | 通过，正常退出 |
| PTY 终端 | 重编译后通过 |
| 文件锁 | 通过 |
| sharp 图片生成 | 保留 WASM 路径后通过 |

这些结果支持“CentOS 7 用户态适配有条件可行”，还不能证明真实 3.10 内核、真实模型网关或全部图片附件流程已通过。

## 调研采用的适配方法

1. 使用支持 glibc 2.17 的 Node 22 构建。
2. 随应用携带兼容的私有 C++ 运行库，不替换系统 glibc。
3. 重编译 `node-pty`；固定 Koffi 3.1.0，并加入一处兼容补丁。
4. 排除不兼容的 sharp 原生包，保留 WASM 实现。调研指出仅依靠自动回退仍可能触发崩溃，明确排除原生包后完整会话通过。

当前 sharp 官方 Linux x64 预编译包要求 glibc ≥ 2.28 和 SSE4.2，因此 CPU 条件满足后，仍不能直接将原生包放入 CentOS 7 离线归档。官方提供 WASM 实现，但不支持原生文字渲染及瓦片输出等部分功能，需检查 DSH 实际使用的功能是否受影响。参见 [sharp 安装与 WASM 说明](https://sharp.pixelplumbing.com/install/)。

私有 C++ 运行库与私有 glibc 是不同事物。私有 C++ 库本身也必须能在 glibc 2.17 上运行，并验证其实际加载路径。HTML 摘要没有给出其完整版本、Koffi 补丁及 WASM 制品细节，正式打包前必须补齐并固定这些输入，或独立实现、验证替代方案。

## 与现有仓库方案的关系

现有包明确排除图片运行时，不允许要求 x86-64-v2 或 WASM SIMD，并对所有 ELF 设置严格的 C++ 符号上限。调研方案不能未经核对就套用现有包名称与兼容性声明；WASM 实际 CPU 要求和私有 C++ 库是否满足现有符号上限都需要审计。

若制作面向环境二的图片增强版，应独立定义构建模式、产物名称、运行库审计规则和验收标准，保留现有 text-only 包的约束。优先复现 sharp WASM 路线；无需因环境一的 CPU 限制，预先决定为环境二重编译整套原生 libvips。

仓库已有的 Node glibc217、PTY 和 Linux 依赖处理可以作为基础，但不能未经比较就叠加调研中的 Koffi 降级及私有库方案。本文仅记录候选路线，没有实现或发布新的图片增强版。

## 尚需完成的验证

1. **真实内核与账户权限。** 在目标机 3.10 内核上验证 bubblewrap、用户命名空间及实际用户的沙箱启动，并完成 Bash、文件读写和 PTY 测试。容器中的 6.12 内核测试不能替代此项。
2. **真实模型网关。** 验证认证、流式响应、`tool_calls` 和工具结果回传。根据用户提供的模型能力，仅声明文本输入。
3. **完整图片附件路径。** 图片生成成功只是初步证明；还需验证 PNG/JPEG/WebP/GIF 的上传、解码、旋转、缩放、重新编码、存储和请求组装。多模态请求组装可使用模拟接口或另一个支持图片的测试模型验证，不能要求当前文本模型完成图片理解。
4. **可复现的离线产物。** 固定源码提交、依赖版本和校验值，验证归档内所有运行库及 WASM 制品的要求，并在目标机不联网、不安装包管理器、不使用 Docker 的条件下验收。

恢复应用的图片附件能力不会使文本模型获得图片理解能力。只有完成上述相关验收后，才能准确说明新包支持哪些功能，不能仅凭当前调研称为“全量功能已验证”。

- 完整容器流程中的产品前后端编译已通过。已修正 legacy hoisted deploy 忽略锁文件造成的 sharp 版本漂移，改用 isolated 部署。
- 固定 sharp `0.35.3` WASM 运行时的 PNG/JPEG/WebP/GIF 编解码、附件存储/读取/缩放、请求图片变体、EXIF 旋转和损坏图片拒绝检查通过；归档 Web 图片入口保留，带认证 Web 启动检查通过。
- Koffi `3.1.1` 使用现有 POSIX stat 回退并静态链接 C++ 运行库，基础 FFI 调用已在断网 CentOS 7 / glibc 2.17 容器通过。无需照搬调研中的 Koffi 降级和私有 C++ 库方案。
- 共用安装器已通过旧 text-only 包首次安装、重复安装、切换到图片版和再次安装检查，用户配置、`.env` 与会话标记均保留。默认数据目录仍为 `~/.local/share/dsh-text-only`。

最终归档含 7 个 ELF，均满足约定符号上限，且没有硬链接。已在 `--network none` 的 CentOS 7 / glibc 2.17 容器中再次通过 CLI、语音组件缺席、文件锁竞争/释放、沙箱 Bash 文件读写、PTY、图片附件及带认证 Web 检查。未把构建机依赖挂载为运行库。

真实 3.10 内核和真实模型 API 仍需目标机验收；容器共享较新的宿主内核。此包是图片增强版，不是语音版，也不声称 sharp WASM 覆盖全部原生功能。切换产品版本前停止旧实例并备份数据，路径共用不保证向旧版降级时的数据格式兼容。
