# dsh-memory 0.8.1 白箱多问法复现

日期：2026-10-16。承接 [26 项可选缺失诊断](dsh-memory-0.8.1-import-diagnostic.zh.md)，本轮只扩大白箱问答样例，不实施修复。

重要范围澄清：下文的 0/32 是独立白箱验证接口的结果，不是普通记忆检索准确率。随后按官方普通记忆链路对相同样例复测，两份包均为 32/32 检索得到包含预期值的事实、8/8 重启后读回；见末尾“正确用法与普通记忆链路对照”。

## 结论

不是只对“项目测试颜色”这一条问题失败。8 组新事实 × 4 种问法，每份包 32 次 `cg(op=whitebox, action=verify_encoding)`，官方 npm 原包与实际离线包各执行一遍，共 64 次。

| 指标 | 离线包 | 官方 npm 原包 |
| --- | ---: | ---: |
| 验证调用数 | 32 | 32 |
| `encoded=true` | 32 | 32 |
| SQLite 中查到完整事实 | 32 | 32 |
| 回答包含预期值 | 0 | 0 |
| `verify_encoding` 返回 `ok=true` | 0 | 0 |

两份包对应的 32 条回答文本逐字节一致。这里是 8 个不同事实、每个事实重复验证 4 次，不是 32 个不同事实。

“包含预期值”是字面检查，不是通用语义准确率。尤其错误前提的是非问，正确回答也可能只说“不是”，不包含目标值；因此本轮另行查看了这些原始回答，实际均未给出对该错误前提的有效纠正。不能把本轮的 0/32 外推为所有问题的总体准确率。

每组还执行了三种变体：

- 换一种说法，例如“访问星舟服务需要填写什么端口号？”。
- 带记忆提示词，例如“还记得之前说过的星舟服务端口是多少吗？”。

## 对照与默认自检

- “你好”：正常返回欢迎语，说明接口不是完全失效或没有响应。
- “什么是条件论？”：返回“可以看‘条件论’……”的相关知识卡提示，但这不是完整定义，不能仅凭非空就判定问答质量通过。
- “为什么高原上煮饭不容易熟？”：两份包都回答“可以看‘生物学’……”，没有回答气压/沸点原因。
- 没有保存过事实时，问“未提供过的紫杉项目的测试颜色是什么？”：也转到“拖延启动”，说明没有可靠地拒答这个未知事实问题。
- 不传自定义 `marker/fact/question`，只运行上游默认 `verify_encoding`：两份包均返回 `encoded=true`、`recalled=false`、`ok=false`，回答“这是我们第一次聊这个话题……”。默认场景同样复现，不只取决于我们设计的颜色问题。

需要收紧之前“白箱已有知识验证通过”的说法：上轮测试遵循上游返回的 `ok` 与回答非空判据，验证的是接口可调用，不是对答案正确性的独立评测。本轮对照说明，两者不能混用。

## 隔离与边界

- 固定 CentOS 7、禁网容器，使用离线包的 Node.js 22.23.2 与 Python 3.12.8。
- 归档 SHA-256、npm SHA-512 和 208 个运行时 Python 文件一致性检查沿用原诊断入口。
- 每份包、每组事实均使用独立 MCP 进程、记忆根和白箱 SQLite 图库；每条问题使用独立会话标识，避免前一道问题的会话上下文提示答案。
- 为节省反复播种耗时，先按原包默认流程生成初始知识库，再将已退出进程的种子数据库复制给本组各事实，之后正常执行写入和问答。没有替换检索实现或模拟回答。
- 每次验证后，用只读 SQLite 查询确认完整事实仍存在。两份包只共享本轮临时本地凭据，不共享记忆库；没有使用真实用户数据或真实模型网关。
- 本轮测试的是 **白箱入口**。不能把结果等同于 DSH 常规大模型聊天、自动 hooks 或核心 `cg(read)` 全部失效；后者有独立的持久化/检索测试。
- 尚未对 NumPy 补齐做 A/B 实验，也未完成白箱根因与修复验证。本轮扩大了复现范围，没有确定缺失依赖是根因。
- 未修改插件源码、安装脚本、现有离线包或真实用户配置；没有发布 GitHub issue。

## 正确用法与普通记忆链路对照

2026-10-16 对照查询官方 README、功能调用映射和实现。所查 main 为 `d8aa3dfedf8d2337da17925a1e5943c958c16940`；执行测试仍使用当前 npm 0.8.1 输入，没有换成最新源码运行。

官方入口区分：

| 目的 | 正确入口 | 返回内容/用途 |
| --- | --- | --- |
| 用户显式归档长期记忆 | `cg(op=write)` | 文本按默认策略组织 CCG 六要素；确认 `committed=true` |
| 插件自动记忆内部写入 | `MdcgClient.remember()` → `mdcg_remember(gated=true)` | 经过主动遗忘闸门；不能只凭 `ok=true` 判断落盘 |
| 普通记忆查询 | `cg(op=read, query=...)` / `mdcg_recall` | 返回事实候选供宿主模型使用，不负责直接生成最终自然语言答案 |
| 白箱能力独立验证 | `cg(op=whitebox, action=verify_encoding)` | 白箱库写入口令后追问，检查是否命中；不是普通记忆查询入口 |

来源：[官方 README](https://github.com/FuRongJun-1999/dsh-memory/blob/main/README.md)、[官方功能调用映射](https://github.com/FuRongJun-1999/dsh-memory/blob/main/docs/mdcg/功能调用映射表_v0.1.md)、[当前 npm 提交的白箱实现](https://github.com/FuRongJun-1999/dsh-memory/blob/32ac237fb56afa43f73d668f1dfe9b306d71b025/md_cg/whitebox.py)。旧文档仍含 AEIS 子进程等历史描述，实际当前默认是进程内自带白箱；本次结合实现核对，没有要求额外启动 AEIS。

### 同样 8 组事实的普通记忆复测

复用相同输入和隔离容器，以插件内部自动记忆的实际客户端路径写入，importance 为文档默认的 0.6，不用 0.95 强制保护分支。每组独立 MCP 根，每次写入后按节点 ID、相同的 4 个问句查询，再重启进程读回。

| 指标 | 离线包 | 官方 npm 原包 |
| --- | ---: | ---: |
| 自动记忆客户端写入返回 ACCEPT 且有节点 ID | 8/8 | 8/8 |
| 按节点 ID 读取包含预期值 | 8/8 | 8/8 |
| 相同 32 个问句的检索候选包含预期值 | 32/32 | 32/32 |
| 重启后按 ID 读回 | 8/8 | 8/8 |
| 额外六要素文本显式写入 | `committed=true`，检索含 34677 | `committed=true`，检索含 34677 |

这里每个记忆根只放一组事实，没有大量干扰文档，所以是正确接口与持久化的冒烟测试，不是大规模检索准确率基准。没有生成真实模型最终答案，也没有模拟或验收完整 DSH 对话 hooks。

因此，若目标是验证“DSH 能否记住并取回用户信息”，前面的白箱入口选择并不合适，不能拿 0/32 代表普通记忆能力。另一方面，白箱自检参数符合官方文档，且完全默认自检也失败，所以白箱接口的观察仍成立，不能直接归为调用参数用错。两条结论应分开表述。

### 用户侧建议的验证方式

先让 Agent 保存事实并确认落盘，例如：“请把星舟服务监听端口是 34677 保存到长期记忆；若显式归档需要六要素，请按插件要求组织，并确认是否已落盘。”

再让 Agent 调用 **cg 工具**（不是终端命令）查询：

```json
{"op":"read","query":"星舟服务 端口","k":5}
```

模型应根据返回节点中的事实回答 34677，而不是拿 `whitebox(action=ask)` 当成这条普通记忆的读取入口。默认 `tools: core` 只暴露 cg/stg，插件内部仍能使用细粒度写入通道；不需要仅为此把工具面改成 all。

复测命令沿用上文容器入口，将报告目录改为 `.cache/dsh-offline/memory-usage-diagnostic`，最后的开关由 `--questions` 改为 `--usage`。报告为 `offline-usage.json`、`upstream-usage.json`、`usage-summary.json`；实现为 [diagnose-memory-usage.mjs](../scripts/offline/diagnose-memory-usage.mjs)。该模式也是采集结果，不把退出 0 等同于所有功能通过。
