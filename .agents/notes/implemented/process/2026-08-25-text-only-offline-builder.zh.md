# Agent Note: 可复现的纯文字离线包构建器

Status: implemented

[English](2026-08-25-text-only-offline-builder.md) | 中文

## Problem

发布的 Linux x64 依赖集合包含 `sharp`，其原生二进制文件要求 x86-64-v2 微架构级别，WebAssembly 后备实现则要求 SIMD。不具备这两项功能的离线部署主机即使只需要文字会话，也无法加载附件插件。每次更新上游代码后重新修改产品源码不是可复现的打包工作流。

## Decision

独立仓库中的 `scripts/offline/` 构建器通过 `--source` 接收单独的 DeepSeek Harness 产品源码检出目录，生成带版本号的纯文字 Linux x64 归档，并且不修改已跟踪的产品源码。它安装锁定依赖，删除产品源码检出目录的陈旧构建输出，运行官方构建，部署生产包集合，并在执行仅限产物的替换前，将所有运行时包实体化到独立暂存目录。生成的归档和下载缓存留在离线工具仓库，不放进产品源码检出目录。

暂存附件提供方不声明任何图片媒体类型并拒绝图片操作。暂存 Web 组合关闭图片界面，离线覆盖配置关闭需要公网的 Web 搜索，包内不包含 `sharp` 及其原生和 WebAssembly 后端。上游包变化导致替换失效时，精确的目录布局断言会终止构建。

归档包含经过校验和验证的 Node.js 22.23.2 `linux-x64-glibc-217` 社区构建、配置示例、许可证和安装说明。推荐入口在固定镜像摘要的 manylinux2014 容器中执行构建，防止原生依赖无意中继承构建主机上的新版 glibc。Linux 产物按照该基线重编 `node-pty` 并静态链接 C++ 运行库，排除仅供 Windows 使用的 Koffi、ACL 与进程包，并通过 `--expose-internals` 启动 Node，不再包含 require-builtin 原生桥。

构建器下载当前检出所声明版本的官方 Linux x64 Landlock 平台包，并在将其中的静态 `landlock-run` 可执行文件装入暂存平台包之前验证固定 SHA-512。源码版本不匹配、可执行文件缺失、ELF 架构错误或内核探测失败都会终止构建。构建器会解压完成的归档，再次执行启动器检查和探测，使归档操作无法静默遗漏二进制或其可执行权限。

打包过程解除硬链接，记录源码提交及运行时版本，拒绝需要高于 `GLIBC_2.17`、`GLIBCXX_3.4.19` 或 `CXXABI_1.3.7` 符号的暂存 ELF 文件，写入 SHA-256 校验文件，解压完成的归档，并针对解压文件运行 CLI、附件、Landlock 和带认证的 HTTP Web 冒烟测试。

构建器在归档旁渲染一份 Bash 4 安装启动脚本。维护者在分发前将脚本的 `PUBLIC_ARCHIVE_PATH` 设置为共享文件系统中的固定软链接，并在旁边提供 `settings.yaml`；用户不输入路径。修改文件前，脚本会报告安装与启动操作并要求明确确认；自动化流程传入 `--yes`。该脚本从复制到本机的归档安装缺失版本，保留 Harness 主目录，已有带版本号的安装不再复制归档，刷新离线 patch，报告本地沙箱可用性，并以前台方式启动 Web。安装脚本不验证发布的校验文件，因此维护者必须在分发前验证。构建过程运行脚本的首次安装与已有安装路径，并通过安装后的命令执行带认证的 Web 冒烟测试。

## Alternatives considered

**为基线 CPU 修改产品源码。** 这种方式会把部署限制混入常规运行时行为，并要求每次上游更新后重新协调相同修改。仅替换产物可以保持官方检出不变，并将上游不兼容明确表现为构建失败。

**将生成的归档提交到 Git。** 这种方式会让仓库检出包含交付载荷，但庞大且不透明的对象将永久扩张仓库历史。[仅通过 Release 交付离线包的决策](2026-08-31-release-only-offline-bundle-delivery.zh.md)将归档、校验文件和渲染后的安装指南保存在带版本号的 Release 资产中，同时让 Git 保留可审查的构建器和文档源文件。

**要求所有部署主机提供 x86-64-v2 或 WebAssembly SIMD。** 这种方式保留图片附件支持，仍是功能完整部署的首选方案，但无法服务 CPU 暴露模型不可调整的受控老旧虚拟机。

**通过单独安装的 glibc 2.35 目录启动现代发行版运行时。** 只有 loader 与 `libc.so.6` 并不能构成完整的隔离运行时，将它们与宿主的旧版 NSS、解析器、locale 及 loader 环境混合使用并不可靠。按照宿主原生 glibc 2.17 构建离线包，可以保留常规且可测试的启动方式。

**在 manylinux2014 容器内编译 `landlock-run`。** 启动器发布流程要求原生 musl 工具链，并将经过验证的静态二进制作为平台包发布，而 glibc 基线镜像不提供 `musl-gcc`。复用采用固定校验和的不可变官方平台包，可以保留启动器发布单元，也避免在离线构建器中额外安装未锁定的编译器。

## Consequences

更新后的检出可以通过一条命令生成新的离线归档，生成的包可在 Linux x64 glibc 2.17 上运行，无需 musl、私有 glibc 目录、npm、pnpm、互联网访问、sudo 或 CPU 模拟。部署保留文字会话和 Linux 本地工具，但放弃全部图片附件及 Windows 行为。支持 Landlock 的目标机使用包内启动器；Linux 3.10 部署环境必须提供可用的 bubblewrap，因为该内核早于 Landlock。

用户可以从共享资产目录运行一份 Bash 脚本，完成首次安装及后续启动。带版本号的程序目录可以共存，`~/.local/bin/dsh` 选择指定包，共享 Harness 主目录保留配置与会话；预发布存储格式仍不承诺降级兼容。

构建仍要求 Docker 或等效的 glibc 2.17 Linux x64 工具链、允许强制 Landlock 探测的宿主内核，并且首次需要访问锁定依赖、固定版本的容器镜像、选定的 Node.js 发行目录、固定 Landlock 平台包，以及重编 `node-pty` 时使用的固定版本 node-gyp 工具。更新原生包版本时，必须先更新构建器中的离线 URL 和 SHA-512，之后才能生成新归档。
